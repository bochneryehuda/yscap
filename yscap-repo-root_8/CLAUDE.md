## Repository layout gotcha

The entire project lives in the **`yscap-repo-root_8/`** subfolder of the git root — `package.json`, `src/`, `db/`, `web/`, `app/` are all there, not at the git top level. Run all `npm` commands from inside `yscap-repo-root_8/`. Render auto-detects this nested `package.json`; deploys run from that folder.

## Commands

Backend (run from `yscap-repo-root_8/`):
- `npm start` — run the server (`node src/server.js`). Serves the API + the static site in `web/`.
- `npm run dev` — same, but with `RUN_SYNC=1` so the ClickUp/Encompass sync worker also starts.
- `npm run migrate` — apply `db/*.sql` manually. **Usually unnecessary**: the server auto-migrates on boot (see below).
- `npm run create-admin -- <email> <password> [role] [full name]` — seed/reset a staff super-admin (also driven by `ADMIN_EMAIL`/`ADMIN_PASSWORD` env on boot).

Frontend SPA (run from `yscap-repo-root_8/app/`):
- `npm install && npm run build` — builds the React portal **into `../web/portal/`**. Render does NOT build the frontend, so **after any change under `app/src/`, rebuild and commit the regenerated `web/portal/` bundle** or the change won't deploy.
- `npm run dev` — Vite dev server for local portal work.

There is **no test runner configured**. Verification in this repo is done by running the server against a local Postgres and exercising endpoints (e.g. ad-hoc Node scripts using `fetch` against `app.listen(...)`, or `require('./src/server')` which does not auto-listen). A real Postgres is required — the code has no in-memory/mocked DB.

## Environment / config

All config comes from env vars, centralized in `src/config.js` (which also loads a bundled `.env` at the project root if present, never overriding real env). Key ones: `DATABASE_URL` (required — unset makes pg fall back to localhost and every request fails with `ECONNREFUSED`), `JWT_SECRET`, `SSN_ENCRYPTION_KEY` (both refuse the dev default in production and generate an ephemeral value + warn), `EMAIL_PROVIDER` (`auto` infers from `RESEND_API_KEY`/`MS_*`), `NOTIFY_FROM`, `APP_URL`, `STORAGE_DIR` (point at a Render persistent disk in prod), `INTAKE_API_KEY`. `render.yaml` is the source of truth for the production service + Postgres + persistent disk.

## Architecture

**One Express process serves everything** (`src/server.js`): the JSON API under `/auth` and `/api/*`, plus the static marketing site and prebuilt SPA out of `web/`. On boot it runs `src/migrate-boot.js` → `ensureSchema()` (waits for the DB, applies `db/schema.sql` only if the base tables are missing, then the idempotent numbered migrations every time) and `bootstrapAdmin()`. `/api/health` probes the DB (200/503).

**Migrations** (`db/`): `schema.sql` defines base tables and is NOT idempotent (bare `CREATE TABLE`) — it runs only on an empty DB. `002_`…`NNN_*.sql` are all `IF NOT EXISTS` / `ON CONFLICT` and safe to re-run on every boot. Adding schema = a new numbered file that is idempotent.

**Two front-ends, one origin:**
- `web/` — the existing static marketing site + standalone tools in `web/tools/*.html` (rehab budget, track record, loan application, term sheet…). The site's pricing/guideline engines (`window.YSP`/`GSP`/`TitleCost`) are **frozen** and must never be modified except by an explicit owner-directed guideline change (see the frozen-baseline note under Session rules). Officer branding is `?lo=<code>`-driven (`web/brand.js`); the loan-application officer dropdown is now fed live from `GET /api/roster` with the static list as fallback.
- `app/` — the React (Vite + HashRouter) borrower/staff portal, built to `web/portal/` and served at **`/portal/`**. Because it's under `/portal/` with a HashRouter, all portal deep links (and email links) must be `/portal/#/<route>` — see `src/lib/email/catalog.js` `link()` and `cfg.portalPath`.

**Auth** (`src/auth/index.js` + `src/lib/crypto.js`): borrowers self-register; staff are admin-provisioned/invited. Custom HS256 JWT, scrypt password hashing, TOTP MFA, and AES-256-GCM SSN encryption — all on Node's built-in `crypto`, **no native deps** (only `express` + `pg` are installed, so Render builds cleanly). Session revocation via a `token_version` claim checked against the DB. A pending-MFA "challenge" JWT carries `mfa:true` and must never be accepted as an access token.

**Roles & authorization:** staff roles are `super_admin > admin > {loan_officer, processor, underwriter}`. `super_admin` satisfies every `requireRole` gate. `seesAll` (admin/super_admin/underwriter) see every application; loan_officer/processor are scoped to files they're assigned to (enforced by a path-scoped middleware on `/applications/:id` and explicit checks on borrower/SSN/document reads). Only a super_admin may modify another super_admin or grant that role.

**Data model** (`db/schema.sql` + migrations): `borrowers` (PII) is separate from `borrower_auth` (login) to reduce blast radius. A borrower has many `applications` (one per property); `llcs` and `track_records` hang off the borrower. `checklist_templates`/`checklist_items` drive the document/condition workflow (audience borrower/staff, RTL phase workflow in `005`). `documents` reference bytes stored via `src/lib/storage.js`. `staff_users` is the single source of truth for the team roster (`007`). `leads` (`008`) captures public marketing-tool submissions. `notifications` (in-app + email fan-out), `sync_queue` (ClickUp/Encompass, deferred), and `audit_log` (GLBA PII trail) round it out. SSNs are encrypted at rest and stripped from any `raw_intake`/`payload` jsonb via `src/lib/redact.js`.

**Notifications & email:** `src/lib/notify.js` always writes an in-app `notifications` row and best-effort fans out a branded email. Email provider is selected in `src/lib/email/index.js` (`resend`/`graph`/`noop`); messages are built by `src/lib/email/catalog.js` and rendered by `src/lib/email/template.js` (table-based HTML, LIGHT/white-first PILOT palette, with the site PILOT lockup image `web/(v2/)assets/brand/pilot-lockup-email.png` via `APP_URL` — see the light-email session rule below). A failed send never breaks the request.

**Storage** (`src/lib/storage.js`): pluggable provider (`local` default, `s3`/`sharepoint` stubs share the interface). `local` persists under `STORAGE_DIR` with path-traversal defense, atomic writes, sharded dirs, and streaming reads. It probes writability and falls back to a temp dir (logging loudly) if `STORAGE_DIR` can't be written, so uploads never hard-fail; `/api/health` reports `storageWritable`/`storagePersistent`/`storageBase`. On Render the default filesystem is ephemeral — `STORAGE_DIR` must point at a mounted persistent disk (currently `/var/data/uploads` on a mounted 5 GB disk). Downloads stream through `src/lib/serve-document.js` after an authorization check.

- **MANDATORY two-audit-agent gate on EVERY change (owner-directed, 2026-07-12):** every single change — a new feature, a bug fix, an error fix, a rewrite, a refactor, anything good or bad, large or one line — MUST be put through **at least two dedicated audit agents**, no exceptions.
  1. **Pre-merge audit (before it lands on `main`):** the moment you finish writing a change, spawn a dedicated audit agent whose job is to troubleshoot **every step, every line, and every way of operation** of what you just wrote. It must confirm the change is (a) implemented in **every place it possibly should be** (all surfaces — marketing site, borrower login, staff/internal login; all roles; previous AND future files; backend AND frontend), (b) actually works end-to-end, (c) does **not** break or regress anything else, and (d) does not mess up at all. It reads the actual diff and the surrounding code, not a summary.
  2. **Post-merge audit (after it lands on `main`, at a HIGHER bar):** after the merge, reopen the audit agent at an even more rigorous level to confirm it was **merged correctly** and that **every single thing works as expected after the merge** (verified against the merged `main` state — NOT waiting for a deploy; "works after merge, not after deploy").
  3. **Any issue found in either audit is fixed IMMEDIATELY without asking for confirmation, and then re-audited** (run another audit pass) until clean.
  4. **Pipeline, don't block:** while an audit is running, immediately proceed to start writing the **next** item on the task list; check the audit's results once the next item is written, act on them, then continue. Never idle waiting on an audit.
  5. **Finish the whole list, then sweep:** never end a session before you have worked on **every single item** the owner put on the task list. After the last item, go back and re-review the **entire** session end-to-end to confirm every item was actually built, nothing was forgotten, and everything composes together. Only ask the owner questions at the very end.
  6. **NEVER let a background/audit agent switch git branches (`git checkout`) in the shared working tree (learned 2026-07-12).** Subagents share ONE on-disk working tree with the main session. If an agent does `git checkout main` (or any branch/commit checkout) while you are mid-work, it **detaches HEAD out from under you** — a commit you make then lands on a detached HEAD and is orphaned when the agent checks back, and files from your branch vanish from disk (a migration "disappeared" and a commit was left dangling this way). Reproduced live against Nominatim: querying that exact address returns `addresstype:"road"`, `display_name:"2nd Street, Piscataway Township, …, 07063"`, which `osmComponentsToAddress` + `canonicalOneLine` render as the corrupted string byte-for-byte. It then went out to the card AND was written back onto `applications.property_address`, AND was cached FOREVER in `address_canon_cache` — so every later correction re-derived the same wrong text instantly, with no network call. That permanent cache row is what turned a one-off bad match into a self-reinforcing loop.
  1. **The chokepoint is `address.geocodeRewriteIsSafe(ours, provider)`** (pure, unit-tested). A provider answer may only RESTYLE: it is refused when it drops or changes the **house number**, disagrees on a **ZIP we already hold**, or drops a **leading directional** ("S 2nd St" and "2nd St" are two different streets). Everything legitimate still passes — abbreviating ("26 South 10th Street" → "26 S 10th St"), normalizing the mailing city, and FILLING a ZIP we never had. `withCoords` now takes the provider's **coordinates** either way (so the address still reaches the ClickUp location field — the 2026-07-26 bug) but keeps OUR text unless the rewrite is safe.
  2. **Precision is enforced at the source too.** `address-canon.parseOsmResult` (extracted pure, mirroring `parseGeocodeResult`) marks a match with no `address.house_number` as `precision:'road'` and returns `formatted:null` + `zip:null`, so nothing downstream — and no cached row — can adopt a road's text; `parseGeocodeResult` now rejects `route`/`postal_code`/`neighborhood`-level Google matches outright, which matters twice because `canonicalize` also backs **`samePlace`**: a road-level `place_id` would make every house on one street compare as the SAME property. For the same reason `withCoords` does not adopt a road-level `place_id`.
  3. **The INBOUND half is what closed the loop.** ClickUp still held the corrupted value and `property_address` COALESCE-overwrites on every pull, so each correction was read straight back over. `clickup/ingest.js` refuses an inbound subject address carrying **no house number when the one we hold has one** (`cols.property_address = null` → COALESCE keeps ours), audits it (`clickup_pull_address_no_house_number`) and re-pushes the good value to repair the card. Deliberately NARROW — every real address has a number, so a human's edit in ClickUp (including a house-number CHANGE) still flows in untouched.
  4. **Previous files: `address-heal.healDowngradedGeocodeCache`** at boot. A row whose QUERY named a house number and whose cached answer doesn't (judged by the same `geocodeRewriteIsSafe`) is provably downgraded: an `osm:` row is blanked to `formatted=NULL, zip=NULL` keeping its coordinates (exactly what the fixed parser now caches), a Google row is DELETED (its `place_id` is the road's identity). Self-draining, idempotent, never throws.
  5. **A SECOND corruption on the same file proves the rule is about more than street-level matches.** Google normalizes "1727 S 2nd St, Piscataway, NJ 08854" to "1727 S 2nd St, Plainfield, NJ 07063" — a PRECISE, rooftop match. The US Census geocoder resolves BOTH: they are **two different houses ~130 m apart** on opposite sides of the Piscataway/Plainfield municipal line, where S 2nd St keeps its numbering across the boundary. Adopting the "better" answer moved the file to a different building. The ZIP check catches it. **A geocoder is not an authority on which property the file is about.**
  Test `scripts/test-address-downgrade.js` (in `npm test`; pure + DB-gated) pins the owner's real strings, the verbatim live Nominatim payload, both corruptions end-to-end through `withCoords`, and the cache repair. When adding any new geocoder or any code that writes a provider's address string onto a record, route it through `geocodeRewriteIsSafe` — never adopt `formatted_address` because "the geocoder answered".

The revocation check rides inside the SAME auth query and **fails OPEN** (a missing table degrades per-device sign-out; it must never 503 the portal).
  3. **THE CHOKEPOINT — after `authenticate()` proves the session, `res.status` is wrapped so no downstream handler can answer 401 (401 → 502).** The SPA reads ANY 401 as "your session died" and wipes the token (which lives in `localStorage`, so it drops every tab on the device). Dozens of routes relay an upstream vendor's HTTP status verbatim (`res.status(e.status)`) — Sitewire, TrustPoint, ClickUp, credit — so a rotated vendor token used to sign the STAFFER out of PILOT. Three modules had worked around it individually (`sync-file-review.js`, `clickup/relink.js`, `sync-autoresolve.js` each document the trap with an `expose` flag); the wrapper kills the whole class at one point, for every route present and future. Do NOT remove it, and do NOT "fix" a route by re-relaying a 401.
  4. **Every session rejection names its reason, and the SPA confirms before signing anyone out.** `sessionDenied()` answers `{error, code, session:'invalid'}` with `code` ∈ `bad_token | mfa_incomplete | wrong_token_kind | session_revoked | signed_out | account_deactivated`, and logs one line — "why was I signed out" is answerable from the logs, not guessed. Client side (`app-v2/src/lib/api.js`, mirrored in the frozen V1 `app/src/lib/api.js`): a 401 no longer signs anyone out on its own — `handle401` probes `/auth/me` once (single-flight, plain `fetch` so it can't recurse) and clears the token ONLY if that also 401s, then shows the SERVER's wording ("This account has been turned off") instead of the generic expiry notice.

It now refuses at the door with `account_deactivated`. **Operational note: if `/api/health` ever shows `jwtStable:false`, `JWT_SECRET` is unset in the environment and every restart/deploy invalidates every session in existence — that alone reproduces this complaint and no code change can fix it.** Test `scripts/test-auth-session.js` (in `npm test`, no DB needed).
- **A BORROWER'S NAME IS FOUR FIELDS PLUS ONE BIG ONE — and `full_name` is what everything reads (owner-directed 2026-07-27; design `docs/NAME-SPLIT-RESEARCH.md`, db/345 + db/346).** PILOT stored a person as first_name + last_name only, and every one-line name from ClickUp was cut with `lastIndexOf(' ')` — so a middle name silently became part of the FIRST name ("Issac Michael" / "Grunzweig") and a generational SUFFIX became the LAST name ("John Michael Smith" / "Jr").   1. **The columns.** `middle_name` (optional — NULL means the person has none), `name_suffix` (Jr./III/MD, kept OUT of last_name so the surname compares cleanly), `name_review_needed` + `name_review_reason` (a PROMPT, never a gate — nothing on a file ever waits for it), `name_split_checked_at` (so the boot repair is resumable). **`full_name` (db/346) is a POSTGRES GENERATED COLUMN** built from the four parts — not a trigger, not application code — so the one big field CANNOT drift from the pieces on any write path, present or future.   2. **ONE splitter: `src/lib/person-name.js`** (pure — no DB, no network). The owner's rule is absolute: **two words split in half**, at full confidence, never a review. Three or more words is a judgement call, so every split reports a CONFIDENCE and flags the uncertain ones. Deliberate conservatism you must not "simplify": a bare trailing `V`/`X` is NOT a suffix (it is far more often an initial standing in for a surname, and mis-reading it DELETES the surname); surname particles are STRONG (`van`, `von`, `della`, `dos`, `du`, `ter` — always attach) vs WEAK (`de`, `del`, `la`, `al`, **`ben`** — real given names too, so they only attach when written LOWERCASE, and the split is flagged); `Mac`/`Mc` are deliberately absent; a blank/placeholder name raises NO prompt (the sync mints `Unknown Unknown` shadows in volume). `compareNames` is middle-name TOLERANT — first + surname must agree, a suffix present on BOTH sides must agree (a father and his son are different people), a middle name that one side omits or abbreviates is the same person — and it re-splits a LEGACY merged `first_name` on the fly so no comparison ever depends on the backfill having run.

- **Two borrowers, ONE credit report — merged / separate / one-borrower imports (owner-directed 2026-07-27).** A joint ("merged") credit report is ONE document covering BOTH borrowers, and it used to be unimportable: `parse.js` de-duped scores per bureau across the WHOLE document, so the second borrower's three scores were silently dropped and the "middle" score was the median of six numbers belonging to two different people; the upload path forced exactly one borrower (`selBorrowers.length === 1`), so the screen simply refused the file. Now:
  1. **`parse.js` SEGMENTS a merged document per borrower** (`parsed.borrowers[]`, `parsed.isMerged`). Ownership of each score/tradeline/inquiry/record is established three ways, in order of certainty and never guessed: STRUCTURE (the item sits inside that borrower's own subtree — MISMO 3.x `PARTY/ROLES/ROLE/BORROWER`), EXPLICIT LINK (`_BorrowerID`/`BorrowerID` naming the borrower's `_ID` — MISMO 2.x), then a 3.x `RELATIONSHIP xlink:from/to` arc. Unclaimed TRADELINES read as JOINT (they appear on both borrowers flagged `sharedAcrossBorrowers`); an unclaimed SCORE is given to NOBODY (`mergedUnattributedScores`) — an unlabelled score could price the wrong borrower's deal. The per-bureau de-dupe now runs INSIDE each borrower. A single-borrower document is byte-for-byte unchanged (an empty `<BORROWER>` placeholder is not a second borrower).
  2. **`match.js` ties the report's people to the FILE's borrowers** in strength order — `ssn` (last-4, proof) → `name` (first+last) → `lastName` (unique remaining) → `order` (one each left, no name contradiction; `verified:false`).   3. **`index.js` imports three ways.** MERGED = one file → a `credit_reports` row EACH (own slice, own middle score, own FICO), the one physical PDF/XML filed ONCE and shared by both rows (`store.storeImport({reuseDocs})`, filenames `credit-report-merged.*`).
