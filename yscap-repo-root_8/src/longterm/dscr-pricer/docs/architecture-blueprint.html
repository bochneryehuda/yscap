02 The question you raised first — sessions & concurrency

Nobody gets bumped, because nobody logs in on demand

Your instinct is exactly right, and it is the single most important design decision. The naive way to build this — have the system log into Lender Price fresh every time someone opens the form — is precisely what causes people to knock each other offline. The fix is to separate two different ideas of "session" that get confused all the time.

Their session with us

Each borrower or staff member has their own isolated workspace in our app: their own inputs, their own results, their own saved scenarios. Fully private, one per person, as many at once as we like.

Our connection to Lender Price

One shared, always-warm login that our backend manages centrally — refreshed quietly before it expires. Users never touch it and never trigger it, so they can't invalidate each other's.

This works because two facts held true in the recording: the pricing call is stateless — each search is independent and saved under its own ID, so parallel searches don't collide — and the login carried no single-session lock (limitOneSessionPerLoanApp: false). One warm token can safely serve every concurrent pricing request.

If we're wrong

If Lender Price turns out to enforce one active token per account under load, the same design absorbs it with no rewrite: run a small pool of service logins behind the token manager, and hand each pricing request the next free one. Users still never log in themselves. This is a config change, not a redesign — which is the point of putting a manager in the middle.

03 The backend, and the wall around the credentials

One service in the middle, credentials behind a wall

The frontend never talks to Lender Price directly, and never sees the Lender Price password or token. Everything goes through our own small backend service — the "agent." That wall is what makes it secure: a borrower's browser only ever holds a short-lived ticket to our system, never anything that could log into Lender Price.

One request, seven steps, a couple of seconds

This is the actual sequence — the same order the recorded browser used, minus the parts a headless agent doesn't need. Steps 3 and 4 are the small lookups Lender Price runs before pricing; step 5 is the one big call.

05 Building it so it can't hurt us

Security & robustness, decided up front

Do this now

The recording you sent me contains your real Lender Price username and password in plain text. A HAR file captures everything the browser sent, including the login. Please treat that file as a secret — don't email or re-share it — and it's worth changing that password, since it has now left your machine. The production system will never store the password the way that file does.

🔑 Credentials in one place

The Lender Price login lives only in a secrets manager, read by the token manager at runtime. Never in the code, never in the repo, never sent to a browser, never written to a log.

🎫 Short-lived, refreshed quietly

The token lasts an hour. The manager refreshes it a few minutes early using a single-flight lock, so a hundred simultaneous requests trigger at most one refresh — never a stampede of logins.

🛡️ Our own front door

Users log into our app (the shared identity you already have), not Lender Price. We decide who can price, we rate-limit them, and we can shut one user off without touching anyone else.

🧱 Fails softly

Timeouts, retries with backoff, and a circuit breaker: if Lender Price is slow or down, one request fails cleanly with a clear message — it doesn't hang the whole system or spin a retry storm.

🧾 Every price is logged

Who priced what, when, and the exact inputs and result — an audit trail. Important for a regulated mortgage context, and it lets us reproduce any quote a borrower questions later.

➗ Stateless workers

Because each pricing call is independent, we can run several copies of the backend for scale and reliability; any one can handle any request. No shared in-memory session to corrupt.

06 How we connect — and the rules we hold

Internal calls only, and three hard "never"s

Settled: we do not use Lender Price's official API. That's a separate subscription on a separate account. We drive the same calls the website itself makes — the ones we've now decoded from your recordings — using your existing view access. This is a pricing viewer: it looks, it never books. No loan is submitted, locked, or registered through it.

⛔ Never touch favorites

We never save a scenario to Lender Price favorites and never load one from them — no getDefaultFavorite, upsertFavorites, or setDefaultFavorite. Favorites cause problems; every search is built fresh from our own template.

⛔ Never book, only view

No lock, no register, no application. The tool shows pricing and stops there — which also means there's no risky write path into Lender Price at all.

⛔ Never expose the account

The one shared login stays server-side. Borrowers see prices, never the credential, the token, or that a single YSCAP account is behind it.

Because we only ever read pricing and never write, the whole class of "we corrupted something in Lender Price" risk is off the table by design.

✓ Who uses the screen decided

Borrowers directly. A borrower-facing tool. That raises the safety bar — see the box below on what a borrower is shown and how we guard the door.

✓ Official API decided

No. Separate subscription, separate account. We drive the internal calls with your existing view access — no API keys, no new contract.

④ How married to the term sheet?

Is this pricer a standalone screen, or does its output feed the separate DSCR term-sheet generator you mentioned? Changes what the result needs to carry.

Because it's borrower-facing

The recorded prices are wholesale. That rate stack — with points and lender compensation baked in — is what a broker sees, not a clean consumer quote. Showing it to a borrower raw would be confusing at best and a compliance problem at worst. So the borrower view needs its own layer: the price they see should be the one you decide to show (e.g. your rate after margin), with the right disclosures — not a naked dump of the wholesale board. The full detail stays available to staff.

A public door needs a lock. Even for borrowers, we put our own login and rate-limiting in front, so the tool can't be scraped, abused, or used to hammer Lender Price. My working assumption: borrowers reach it signed into your portal (the identity you already have), not as anonymous web traffic — tell me if you meant a fully public lead form instead.
